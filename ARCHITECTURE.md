# Architecture

This repository defines a reproducible Ubuntu development VM and an optional Docker devcontainer. Vagrant configures VirtualBox; both environments mount host-side project files so they remain the source of truth.

## Components and provisioning

- `Vagrantfile` selects the Ubuntu 22.04 box, configures VM resources, and mounts the repository's parent directory at `/workspace`. The shell provisioner runs as root; `bootstrap.sh` uses `VM_USER` (`vagrant` by default) for the guest user's shell setup.
- `vm-config.json` holds the optional VirtualBox name and editable CPU/memory defaults loaded by `Vagrantfile`. A `null` name delegates to Vagrant's instance-specific name generation to avoid fixed VM-directory collisions; `VM_NAME`, `VM_CPUS`, and `VM_MEMORY_MB` can override the settings.
- `provision/bootstrap.sh` installs system tools (including `jq`), Node.js v22 and npm from NodeSource's 22.x APT repository, GitHub Copilot CLI using the official Linux install script, and VS Code. It also configures the development user's npm with `bin-links=false` for the host-shared VirtualBox workspace. The installer runs as root and places `copilot` in `/usr/local/bin`; Copilot installation does not depend on the development Node.js/npm packages and does not modify user settings.
- `Vagrantfile` passes the mounted repository's `provision/copilot-init.sh` path to the root provisioner. `bootstrap.sh` installs an executable `copilot-init` wrapper beside the Copilot CLI without running it or modifying the guest user's profile.
- `provision/copilot-init.sh` is shared by the VM and devcontainer. The VM guest runs it manually; Dev Container creation and the Windows `rmz-container` launcher run it automatically. It derives the repository root from its script path, registers `Ramzza/rmz-ai-marketplace` if it is not already registered, merges `provision/copilot-settings.json` into `~/.copilot/settings.json`, and links repository instructions into `~/.copilot`. Repeat runs reapply managed settings, avoid duplicate marketplace registration, and remove stale links into the former repository skill directory while preserving unrelated preferences and conflicting targets. When `claude` is on `PATH` (the devcontainer), it also runs `claude plugin marketplace add` and `claude plugin install rmz-ai-skills@rmz-ai-marketplace --scope user`, which are idempotent; the marketplace's `.claude-plugin/marketplace.json` points Claude Code at the same skill tree Copilot CLI uses. Without Claude Code (the VM) this step is skipped.
- `scripts/rmz-copilot.sh` and `scripts/rmz-copilot.ps1` run on the host, resolve the repository root, and start Vagrant before opening SSH. Their setup scripts register the `rmz-copilot` function in the user's Bash/Zsh or PowerShell profile.
- `.devcontainer/devcontainer.json`, `compose.yaml`, and `Dockerfile` configure a Linux development container with Node.js v22, Python 3.15, GitHub Copilot CLI, GitHub CLI (`gh`, from GitHub's official stable APT repository), Claude Code (installed for the `vscode` user with its official installer), and the `jq` dependency used by `provision/copilot-init.sh`. It also installs OpenJDK 25 and, as the `vscode` user, the checksum-verified Android SDK command-line tools in `/opt/android-sdk` with `platform-tools`, the platform and build-tools selected by the `ANDROID_PLATFORM` and `ANDROID_BUILD_TOOLS` build arguments, and accepted SDK licenses; `JAVA_HOME`, `ANDROID_HOME`, `ANDROID_SDK_ROOT`, and `PATH` are set in the image. Gradle comes from each project's wrapper. Named volumes persist the GNOME Keyring data, the GitHub CLI configuration directory (`/home/vscode/.config/gh`, whose `hosts.yml` records the account whose token is in the keyring), and the Claude Code configuration directory (`CLAUDE_CONFIG_DIR=/home/vscode/.claude`). Compose bind-mounts the host directory containing this repository's parent at `/workspace`; the workspace is the repository's subdirectory there. Dev Container creation runs the shared initialization script after creation.
- `scripts/rmz-container.ps1` resolves the repository and Compose file relative to the script, so the installed command works from any working directory. It uses Docker Compose with `--build` to rebuild a stale image and create or start the devcontainer, initialize Copilot, and open an interactive shell. Its `--recreate`, `--stop`, and `--down` options rebuild/recreate, stop, or stop/remove the container; `scripts/setup-rmz-container.ps1` installs the command in the Windows PowerShell profile.
- `.github/copilot-instructions.md` and `provision/copilot-settings.json` are canonical VM and devcontainer assets. Skills are distributed by the `rmz-ai-skills` plugin in `Ramzza/rmz-ai-marketplace` and are installed separately through Copilot CLI; `copilot-init` does not copy skills or install them for Copilot CLI, but installs the plugin for Claude Code when it is present.

## Lifecycle and data flow

`vagrant up` creates or starts the VM and runs provisioning on initial creation by default. The root provisioner installs Node.js v22 and the current stable Copilot CLI release system-wide, configures the development user's npm for the mounted workspace, registers the separate `copilot-init` command, and configures the guest user's shell. It does not create or modify `~/.copilot`; the guest user opts in by running `copilot-init` after provisioning. Project files are edited in the mounted workspace, so they persist independently of VM recreation.

`vagrant provision` or `vagrant up --provision` reapplies setup after provisioning changes. The VM defaults to 4 CPUs and 8192 MB of memory as defined in `vm-config.json`; the `VM_NAME`, `VM_CPUS`, and `VM_MEMORY_MB` environment variables override their respective values.

The devcontainer uses Docker Compose to build and start its container, then runs the shared Copilot initialization script. The Windows `rmz-container` command also runs the script before opening a shell in `/workspace/<repository-folder>`, regardless of the caller's working directory. Every launch passes `--build`, so Dockerfile changes are picked up (and the container recreated) without a manual rebuild; `--recreate` also forces container recreation; `--stop` stops the service, and `--down` removes it after stopping.

## Validation

The shell and devcontainer contract tests run with `bats tests`; the GitHub Actions workflow also runs the PowerShell host-command tests on Windows.
